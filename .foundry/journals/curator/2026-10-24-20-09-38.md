# Journal Entry

During the review of `idea-077-dynamic-pokeapi-data`, I identified a potential architectural overlap with the already PENDING `idea-136-split-bundles-and-data` and `idea-117-split-bundles-and-data`.

`idea-117-split-bundles-and-data` and `idea-136-split-bundles-and-data` both propose splitting the monolithic `pokedata.msgpack` into a core bundle and generation-specific extensions using `vite-plugins/pokedata-plugin.ts` by emitting multiple msgpack bundles.
`idea-077-dynamic-pokeapi-data` proposes adding more data (move PPs, valid items) into `.jsonl` files (e.g. `items.jsonl`, `moves.jsonl`) generated by build scripts like `scripts/generate-pokedata.ts`. The vite plugin will package this for client access, mirroring the pattern used for encounters.

These ideas intersect around the build process for game data (`scripts/generate-pokedata.ts`, `pokedata.msgpack`, vite plugins). The expansion of static data during the build process (Idea 077) should likely be designed in conjunction with the effort to split this data by generation (Idea 117/136).

I have updated the Idea Dependency Matrix (`.foundry/docs/architecture/idea_dependency_matrix.md`) to explicitly link these ideas. I also spawned a new remediation node (`research-077-717-dynamic-pokedata-bundle-splitting-integration.md`) assigned to the `researcher` persona to investigate the overlap and ensure a clean architectural path forward, especially concerning how `items.jsonl` and `moves.jsonl` should be bundled considering the planned generation-based splitting. The new node has been appended to the Acceptance Criteria of `idea-077-dynamic-pokeapi-data`.
