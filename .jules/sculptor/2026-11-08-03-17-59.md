## Refactoring Goal
Improve AI readability and predictable reasoning for Route Radar heatmap calculations in `src/engine/radar/RouteRadarController.ts` by decomposing the 4-level nested loop and mutable dictionary state updates in `calculateHeatmap` into dedicated, pure helper functions (`extractEncounterAreaRequirements` and `updateHeatmapForArea`).

## Actions Taken
- Extracted helper function `extractEncounterAreaRequirements` to isolate the extraction and deduplication of area IDs and bike requirement aggregation from nested encounter structures.
- Extracted helper function `updateHeatmapForArea` to handle safe initialization, density incrementing, and merging bike requirement flags for a target area.
- Streamlined `RouteRadarController.calculateHeatmap` from deeply nested `for` loops into a clear, linear flow that composes the two helper routines.
- Added comprehensive unit tests in `src/engine/radar/__tests__/RouteRadarController.test.ts` testing `extractEncounterAreaRequirements` and `updateHeatmapForArea` across missing encounter info, multiple areas, and bike flag combinations.

## Critical Learnings
- **Deeply nested loops obscure multi-pass data aggregation for AI models:** Nesting outer suggestion iteration, `for...in` record loops, encounter arrays, and Map state mutations inside a single 40-line method forces LLMs to track multiple layers of mutable index state simultaneously.
- **Decomposing into extraction and mutation stages clarifies intent:** Separating data extraction (`extractEncounterAreaRequirements`) from accumulation (`updateHeatmapForArea`) creates predictable pure boundaries. AI agents inspecting or modifying radar density or traversal logic can test and reason about requirement extraction independently from heatmap dictionary mutations.
